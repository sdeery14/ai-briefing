## Q3. Provider and model identifiers — resolved

**Decision (owner, 2026-11-21):** Anthropic, through the Claude API.

| Tier | Model ID | Input / output per million tokens |
|---|---|---|
| Screening and inexpensive processing | `claude-haiku-5-5` | $0.10 / $0.50 for prompts up to 100,000 tokens; $0.50 / $2.50 above |
| Higher-quality assessment and escalation | `claude-sonnet-5-5` | $2.00 / $10.00 |

Identifiers, prices and capabilities were checked against Anthropic's models overview and pricing pages on 2026-11-21. Both models support schema-constrained output, a 1M-token context and 128K output tokens. Full detail and the consequences for the design are in RFC §7.1 and ADR-009.

The $15 monthly application-enforced budget stands. Prices are verified; volumes are not, so the cost illustration in RFC §7.2 is an assumption until M1 measures it.

Still to do, in M0 and by the owner: create a separate API key for AI Briefing with a provider-side spending limit. No key has been created and none is stored in the repository.

## Q7. Initial source catalogue — editorial selection resolved; terms records outstanding

**Decision (owner, 2026-11-21):** nine sources form the initial editorial selection: OpenAI News, Google DeepMind blog, Google Research blog, Hugging Face blog, arXiv (`cs.CL` only), MLflow releases, Simon Willison's Weblog, Hacker News, and Anthropic SDK releases. Details and the remaining candidates are in [`docs/planning/source-catalogue-draft.md`](../planning/source-catalogue-draft.md).

This approves which sources to follow. It does not permit fetching or retaining anything. What remains, per ADR-010:

- A terms record for each of the nine, reviewed and approved by the owner, before that source is enabled.
- Reviewed so far: arXiv's API terms and the Hacker News API README. The record for each still needs the owner's approval.
- Not reviewed: the other seven.

Known limitations, accepted: Anthropic SDK releases are only a partial substitute for Anthropic announcements, and no scraper is built for them now; arXiv starts with `cs.CL` only, with more categories considered after M1 measures volume and relevance.

## Q1. Storage for the data directory — blocks M2

The Home System repository documents microSD boot and an SSD that is planned, not confirmed.

**Default:** the database and stored payloads go on an SSD. If none is attached at M2, add one before deploying.

| Option | Consequence |
|---|---|
| SSD (default) | Meets ADR-008. A small purchase if not already made. |
| Run on another machine | Avoids the Pi's constraints; breaks the same-host file exchange and needs a new transport. |
| microSD with frequent backups | Not recommended. Write wear and corruption risk on a card shared with other services. |

## Q2. Off-device backup destination — blocks M2

**Default:** a nightly encrypted snapshot to a destination that is not the Pi: another always-on machine on the home network or private mesh, or a cloud object-storage bucket. The Pi's own MinIO does not count.

The choice depends on what the owner already has and is willing to pay for. Whatever is chosen, a restore must succeed before first real use.

## Q4. Placement and length in the email — blocks M2

The existing email is a deliberately short personal note of about 150 words. Including the full briefing makes it several times longer.

**Default:** the briefing is a separate, clearly headed section after the existing content, rendered verbatim from the structured fields. The personal note is unchanged and its model call never sees briefing content.

| Option | Consequence |
|---|---|
| Separate section after the note (default) | The note keeps its character; the email is longer. |
| Briefing first, note second | Suits a reader who opens the email mainly for the briefing. |
| A second email from the same integration | Keeps each email short; doubles the send and its failure modes. Home Assistant still owns both. |

Not offered: letting the note's model summarise or mention the briefing. That is a prompt-injection path into a prompt that holds personal context.

## Q5. Authentication for the feedback page — blocks M2

**Default:** the page requires a Home Assistant login, as the existing chat panel does. A device that is already signed in opens it directly.

| Option | Consequence |
|---|---|
| Home Assistant login (default) | Strongest. Depends on the owner's devices staying signed in to be convenient. |
| Signed, expiring token in the link; confirmation form; record on `POST` only | No login. Anyone holding the email can submit; safe against scanners because nothing is recorded on `GET`. |

Either way: no state change on `GET`, and no unauthenticated endpoint that records feedback without an intentional action.

## Q6. Fetching pages on uncatalogued hosts

Hacker News links to arbitrary sites whose terms have not been reviewed.

**Default (in force):** no. Such items are kept as metadata and cannot exceed `watch` unless a catalogued source covers the same story. Hosts that recur are reported so the owner can add them to the catalogue.

Alternative: fetch when `robots.txt` allows, with the same 90-day retention. More evidence for more stories, at the cost of the conservative position in ADR-010. Revisit with M4 coverage data.

## Q8. Agent identity and environment for Phase B

Not needed while the owner merges every pull request.

**Default:** a GitHub App installed on this repository only, with contents and pull-request write access and no administration permission; rounds run in an environment (a container, a separate OS account or a cloud session) where the owner's GitHub credentials are absent.

Alternative: a machine user account. Simpler to set up; a second account to secure.

## Q9. Promoting a judge from diagnostic to authoritative

ADR-007 requires measured agreement with owner labels and owner approval, and deliberately sets no number.

**Default:** decide per judge when data exists. As a starting expectation, not a threshold: agreement measured on at least 100 owner-labelled items that include a meaningful share of negatives, reported with an interval, and re-measured on any change to the judge.

## Q10. Where the weekly labelling session happens

**Default:** on the development machine, from the latest database snapshot. A command produces a worksheet of sampled items without the system's class; the owner fills it in; an import command turns it into label events that are ingested like feedback.

Alternative: a labelling view on the Home Assistant feedback page. One place for all judgements; more to build in the Home System.
